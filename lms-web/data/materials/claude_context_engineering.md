# 컨텍스트 엔지니어링(Context Engineering) — 질문보다 환경이 중요하다
> 원본: claude_context_engineering.pdf · 난이도: ★★☆(곧 필요)

## 한 줄 요약
좋은 답을 받으려면 "질문 문장"보다 모델이 **무엇을 알고, 기억하고, 무시하게 할지**(=컨텍스트)를 설계해야 한다.

## 이게 뭐예요?
프롬프트 엔지니어링이 "말을 잘 거는 법"이라면, 컨텍스트 엔지니어링은 "대화할 **방을 미리 세팅하는 법**"입니다. 똑같은 질문도 어수선한 시장 한복판에서 던지면 엉뚱한 답이 오고, 자료가 정리된 회의실에서 던지면 정확한 답이 옵니다. 클로드가 이상한 답을 내는 건 대부분 "멍청해서"가 아니라, 우리가 만든 잘못된 방(불필요한 기록, 빠진 조건) 안에서 **다른 질문에 답하고 있기 때문**입니다.

## 핵심 정리
- 컨텍스트(context) = 질문 시점에 모델이 보고 있는 모든 것. 프롬프트는 "내가 하는 말", 컨텍스트는 "모델이 딛고 선 바닥".
- 컨텍스트의 4가지 층:
  - **Role(역할)**: "너는 누구로서 답할 것인가". 안 정하면 그냥 '친절한 일반 비서'가 된다.
  - **Task(작업)**: "정확히 무슨 일을, 무엇을 기준으로". 예: "코드 리뷰해줘" 대신 "정확성·위험 위주로 보고, 스타일은 무시해".
  - **Information(정보)**: "지금 진짜인 사실들". 안 주면 모델이 기본값을 지어내거나(할루시네이션) 교과서식 가정을 한다.
  - **Memory(기억)**: "무엇을 유지하고 무엇을 잊게 할 것인가". `/compact`, 메모리 파일, 세션 리셋이 여기 쓰이는 도구.
- 좋은 기억: 안정적인 선호, 확정된 결정. 나쁜 기억: 옛 가정, 하다 만 아이디어, 틀렸던 방향. → "컨텍스트 엔지니어링 = 모델 두뇌의 청소(garbage collection)".
- 컨텍스트가 좋으면 명령은 짧아져도 답이 단호해지고 되묻기가 줄어든다.
- "주니어는 프롬프트를 쓰고, 시니어는 컨텍스트를 설계한다." 우리는 질문이 아니라 **추론 환경**을 만드는 것.

## 따라해보기
1. 같은 질문을 역할 없이 / 역할을 주고 두 번 던져 비교하기:
   ```
   git이 뭐야?
   ```
   ```
   너는 프로그래밍 입문자를 가르치는 선생님이야. git이 뭔지 비유 1개로 설명해줘.
   ```
   → 역할(Role)만 줘도 답의 질이 달라지는 걸 체감한다.
2. 조건(Information)을 넣어 질문하기:
   ```
   조건: 나는 Mac을 쓰고, 터미널은 처음이야. 이 조건에서 폴더 만드는 법 알려줘.
   ```
   → 모델이 내 상황에 맞는 답만 하게 된다.

## 주의할 점 / 자주 헷갈리는 것
- 답이 이상하면 질문 문장만 고치지 말고, 대화에 쌓인 쓰레기(옛 로그, 틀린 방향)부터 의심하자.
- 조건을 안 주면 모델은 빈칸을 "그럴듯하게" 지어서 채운다. 빠진 사실이 없는지 먼저 확인.
- 컨텍스트는 많을수록 좋은 게 아니다. **관련 없는 내용이 많으면 오히려 답이 나빠진다.**
- 멀티 에이전트 설계 같은 고급 활용은 나중에 배워요. 지금은 "역할 + 작업 + 사실"만 챙겨도 충분.

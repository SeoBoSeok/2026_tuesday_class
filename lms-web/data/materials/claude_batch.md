# /batch — 대규모 코드 수정을 병렬로
> 원본: claude_batch.pdf · 난이도: ★★★(나중에)

## 한 줄 요약
/batch는 "코드 전체에 걸친 큰 수정"을 여러 개의 작은 단위로 쪼개서, 에이전트 여러 명이 동시에 처리하고 각각 PR로 제출하게 하는 명령이다.

## 이게 뭐예요?
아파트 전체 도배를 한 명이 하면 한 달 걸리지만, 집집마다 도배공을 한 명씩 보내면 하루에 끝나죠.
/batch가 바로 그 **도배 반장**이에요. "전체 도배해줘"라고 한 마디 하면, 반장이 먼저 둘러보고 작업을 집(단위)별로 나눈 계획서를 보여줍니다.
여러분이 "좋아요" 하면 그제서야 도배공(백그라운드 에이전트)들이 각자 자기 집에서 동시에 일을 시작해요.
각자 작업이 끝나면 검사(테스트)까지 하고 결과 보고서(PR, Pull Request = 코드 변경 제안서)를 하나씩 제출합니다.

## 핵심 정리
- 사용법: `/batch <지시문>` — 높은 수준의 변경 요청 한 줄이면 된다
- 이런 변경에 적합: **넓고**(많은 파일), **반복적이고**(비슷한 수정), **쪼갤 수 있는**(독립 단위로 분리 가능) 작업
  - 예: 프레임워크 마이그레이션, 라이브러리 교체, 이름 일괄 변경, 설정 표준화
- 실행 흐름: 코드베이스 조사 → 5~30개의 독립 단위로 분해 → **계획을 보여주고 승인 대기** → 승인 후 단위마다 백그라운드 에이전트 1개씩 병렬 실행
- 각 에이전트는 격리된 git worktree(같은 저장소의 별도 작업 폴더)에서 일해서 서로 충돌하지 않는다
- 결과물은 단위별 PR 여러 개 → 리뷰하기 쉽고, 일부만 합치거나 일부만 되돌리기도 가능
- 좋은 지시문 = 범위 명확(어느 폴더) + 완료 기준 명확(뭐가 되면 끝) + 제약 명시(동작 바꾸지 마 등)

## 따라해보기
※ git 저장소가 있는 프로젝트에서만 동작해요. 아래는 형식 연습용 예시입니다.
1. `/batch rename all occurrences of FooService to BarService and update imports/tests`
   - 특정 이름을 저장소 전체에서 바꾸고 import와 테스트까지 갱신하는 계획을 세워준다.
2. `/batch replace deprecated API X with API Y across the repo, but preserve behavior`
   - 낡은 API를 새 API로 교체하되 동작은 유지하라는 제약을 단 예시.
3. 계획이 나오면 바로 승인하지 말고 단위 목록을 읽어보기
   - "승인 전에는 아무것도 실행되지 않는다"는 안전장치를 직접 확인한다.

## 주의할 점 / 자주 헷갈리는 것
- **git 저장소가 필수다.** git이 없는 폴더에서는 못 쓴다.
- 작업 단위들이 서로 얽혀 있으면(상호 의존) 머지 충돌이나 중간에 깨진 상태가 생길 수 있다. 순서와 계획이 중요.
- 계획 승인 단계는 귀찮은 게 아니라 핵심 안전장치다. 대충 승인하면 시간과 비용을 낭비한다.
- 작은 수정(파일 1~2개)에는 /batch가 오히려 과하다. 그냥 일반 대화로 시키자.
